# Summoner Tower — правила разработки

## Godot MCP

Для операций, связанных с Godot Editor, сценами, nodes, runtime,
запуском проекта, inspection и playtesting, используй подключённый Godot MCP.

Не редактируй .tscn вручную, если ту же операцию надёжнее выполнить через Godot MCP.

После значимых изменений запускай проект и проверяй runtime errors через Godot MCP.

## 1. Источники требований

- `docs/ТЗ для Codex CLI — Summoner Tower MVP.md` определяет состав и поведение MVP.
- `docs/DEVELOPMENT_PLAN.md` определяет порядок реализации и приёмки фич.
- Последние явные решения пользователя уточняют эти документы и имеют приоритет над правилами этого файла.
- Перед работой читать требования текущей фичи. Существенные противоречия обозначать до реализации; не менять документы задним числом ради соответствия коду.

## 2. Одна фича за раз

- Перед новой фичей описать результат для игрока, игровую логику, затрагиваемые системы, продуктовые решения, технический план, критерии готовности и ручные проверки.
- Начинать реализацию после явного согласования пользователя. Уже согласованная работа не требует повторного разрешения на каждый технический шаг или исправление.
- После реализации самостоятельно проверить фичу, исправить ошибки, дать отчёт и чек-лист ручной приёмки, затем остановиться.
- Следующую фичу начинать после ручной приёмки текущей и согласования следующей. Не строить новую систему поверх непринятой механики.
- Если нужно существенное продуктовое решение вне согласованного плана, согласовать его. Рутинные технические решения принимать самостоятельно, выбирая минимально достаточную реализацию.

## 3. Границы MVP

- Приоритет — приятный работающий core loop, стабильность и понятность. Архитектура и объём контента должны поддерживать эти цели.
- Не добавлять механики и системы за пределами ТЗ. Не создавать универсальные frameworks на перспективу.
- Фича 18 плана: реальные платформенные SDK, реклама и аналитика — отдельный этап после Web MVP, требующий отдельного согласования.

## 4. Фиксированный стек

- Godot 4.x, GDScript, стандартные узлы. Основная платформа — HTML5/Web; локальный запуск в Godot также должен работать.
- Не использовать C#, платные плагины или внешние backend-сервисы для MVP.
- До первой реализации определить фактическую версию редактора и зафиксировать её в технической документации вместе с требованиями к export templates.
- Редактор и export templates должны соответствовать друг другу. Не обновлять движок посреди разработки без обсуждения.
- Значение `config/features` в `project.godot` само по себе не подтверждает версию установленного редактора.

## 5. Web как постоянное ограничение

- Использовать Compatibility renderer и по умолчанию однопоточный Web export.
- До внедрения API, шейдеров, аудиоэффектов и сторонних зависимостей проверять их совместимость с выбранной версией движка и Web.
- Не вводить зависимость от потоков или нативных расширений без обоснования и согласования.
- При сомнении сверяться с официальной документацией именно используемой версии Godot.

## 6. Начальная проверка Godot MCP

- Перед работой через MCP проверить подключение, путь открытого проекта, версию движка и список доступных инструментов.
- Работать только с этим проектом. Не считать текущий редактор автоматически подключённым к нужному workspace.
- Использовать реальные схемы инструментов. Не придумывать команды, параметры или возможности MCP-сервера.

## 7. Разделение работы между MCP и файлами

- Для операций с редактором, сценами, узлами, runtime, запуском, inspection и playtesting использовать подключённый Godot MCP.
- Код и текстовые ресурсы редактировать напрямую, если это быстрее и надёжнее. `.tscn` не редактировать вручную, если ту же операцию надёжнее выполнить через Godot MCP. Для локальных правок использовать `apply_patch`.
- Способ работы выбирать по задаче; не выполнять длинные цепочки MCP-вызовов ради операции, которую безопаснее выразить короткой файловой правкой.

## 8. Согласованность редактора и файлов

- Перед внешней правкой сцены проверить несохранённые изменения в редакторе. Не перезаписывать пользовательскую работу.
- После файловых правок дождаться обновления и импорта ресурсов, затем проверить результат в редакторе или runtime.
- Не изменять одну сцену одновременно через MCP и файловый редактор.
- Не удалять `.godot/` как универсальное средство исправления ошибок. Сначала установить причину.

## 9. Проверка результата MCP

- После значимого изменения проверить соответствующие узлы, свойства, привязки скриптов, сигналы или runtime-поведение.
- Успешный ответ инструмента не означает, что фича работает.
- После значимых изменений игрового проекта запускать его и проверять runtime errors через Godot MCP.
- При недоступности MCP использовать безопасные файловые и CLI-проверки, если они позволяют продолжить согласованную работу.
- Явно сообщать, какие проверки недоступны. Не выдавать непроверенный результат за подтверждённый.

## 10. Редактируемые сцены

- Постоянную структуру экранов, HUD и игровых объектов хранить в `.tscn`.
- Динамически создавать врагов, существ, снаряды и временные эффекты из переиспользуемых сцен.
- Не собирать весь интерфейс большим скриптом, если его удобнее поддерживать в редакторе.
- Сохранять понятное дерево узлов и необходимые ссылки ресурсов. Не пересоздавать UID без причины.

## 11. Простая архитектура Godot

- Разделять ответственность между сценами и небольшими скриптами; использовать композицию и сигналы.
- GameManager управляет игровым циклом, но не поглощает бой, UI, экономику и сохранения.
- Autoload использовать только для действительно постоянных сервисов или состояния между сценами.
- UI отображает состояние и передаёт действия, а правила экономики и боя принадлежат соответствующим игровым системам.

## 12. Стиль GDScript и коммуникации

- Типизировать поля, параметры и возвращаемые значения там, где тип известен. Соблюдать единый стиль Godot и настройки `.editorconfig`.
- Использовать `snake_case` для файлов скриптов, переменных и функций, `PascalCase` для классов и имён узлов.
- Комментарии объясняют причины, ограничения и неочевидные решения; не пересказывают очевидный код.
- Общение и проектная документация — по-русски, идентификаторы — по-английски. Тексты интерфейса соответствуют согласованному языку продукта.

## 13. Баланс в Resources

- Характеристики существ, врагов, волн, цены и бонусы хранить в централизованных `.tres` и соответствующих классах Resource.
- Не разбрасывать балансные числа по скриптам; формулы и правила округления должны иметь единое место реализации.
- Общий Resource с базовыми характеристиками не изменять при усилении отдельного юнита или текущего забега.
- Эффективные характеристики вычислять из исходных данных и текущих модификаторов либо хранить в отдельном состоянии экземпляра.

## 14. Разделение состояния

- Постоянный прогресс, состояние текущего забега и исходные данные баланса хранить отдельно.
- Новый забег полностью сбрасывает временные бонусы, статистику, таймеры и объекты предыдущего забега.
- Постоянные бонусы применять в предусмотренный момент без повторного умножения уже модифицированных значений.

## 15. Явные состояния игрового цикла

- Бой, пауза между волнами, выбор улучшения и завершение забега имеют явные состояния и понятные переходы.
- Управление паузой централизовать. Окно выбора улучшения принимает ввод, пока бой остановлен.
- При завершении забега останавливать спавн и боевые действия. Возврат в меню и рестарт должны корректно работать из предусмотренных состояний.

## 16. Однократное выполнение игровых событий

- Смерть врага, урон башне, выдачу маны, завершение волны и начисление кристаллов защищать от повторного выполнения.
- Различать уничтожение врага игроком и достижение башни; награды выдавать только по предусмотренным правилам.
- Завершать волну, когда закончен спавн и не осталось активных врагов, учитывая врагов, достигших башни.
- Изменение состояния фиксировать до отправки событий, которые могут привести к повторному вызову.

## 17. Цельные операции призыва и merge

- Сначала проверить все условия, затем изменять слоты, юнитов и ресурсы.
- Неудачный призыв не расходует ману и не увеличивает цену.
- Перенос, swap и merge не оставляют промежуточного состояния, допускающего потерю или дублирование юнитов.
- Поддерживать контракт: максимум 6 существ; merge только одинакового типа и уровня ниже Lv5; несовместимые существа и пары Lv5 меняются местами. Предел Lv5 согласован пользователем при уточнении фичи 11.
- Отмена перетаскивания или отпускание вне допустимого слота сохраняет корректное исходное состояние.

## 18. Единая логика мыши и touch

- Ввод обоих типов вызывает одинаковые игровые операции.
- Учитывать масштабирование координат, отпускание вне слота, отмену перетаскивания и захват указателя интерфейсом.
- Исключить двойное действие от touch и эмулированного mouse event.
- Для одного перетаскивания отслеживать конкретный указатель; дополнительное касание не должно перехватывать или дублировать операцию.

## 19. Адаптивный вертикальный UI

- По решению пользователя предпочитать понятные иконки тексту для валюты, действий,
  навигации и характеристик. Краткие подписи оставлять, если без них смысл неоднозначен.

- Базовое логическое разрешение — 720 × 1280; сохранять вертикальную композицию и пропорции, предусмотренные ТЗ.
- Для интерфейса использовать `Control`, anchors и containers. Не привязывать весь UI к размеру одного физического окна.
- Проверять портретные экраны и широкое desktop-окно; боковые поля допустимы.
- Текст должен быть читаемым, кнопки удобными для касания, HUD и модальные окна не должны перекрывать необходимые действия.

## 20. Жизненный цикл объектов

- Проверять актуальность цели снаряда и атакующего юнита; корректно обрабатывать исчезновение цели.
- Освобождать врагов, снаряды и эффекты. Завершать или обезвреживать таймеры и анимации при удалении объектов и смене сцены.
- После рестарта не должно оставаться активных callbacks, сигналов или асинхронных продолжений предыдущего забега.
- Движение и время эффектов не должны зависеть от количества кадров в секунду.

## 21. Сохранения с проверкой данных

- Использовать `user://`, версию формата, проверку данных и разумные значения по умолчанию.
- Сохранять кристаллы, уровни постоянных улучшений и согласованные настройки; текущий забег в MVP не сохранять.
- Отсутствующий или повреждённый файл не должен ломать запуск. Проверять ошибки записи и не сообщать об успешном сохранении при ошибке.
- Сохранять прогресс после значимых операций, а не только при закрытии приложения.
- Проверять сохранение также в экспортированной браузерной версии после перезагрузки страницы и повторного открытия на том же origin. Учитывать ограничения IndexedDB и настроек браузера.

## 22. Воспроизводимая отладка и AdService

- Предусмотреть отключаемые debug-команды из ТЗ и возможность задать seed случайности для повторения проблем.
- Debug UI должен отключаться одной настройкой или отсутствовать в production export.
- Отладочные проверки и команды не должны портить обычное сохранение игрока; использовать отдельные тестовые данные или явный тестовый режим.
- Fake AdService должен поддерживать успешное завершение и отказ/неуспех операции. Награду выдавать только после успешного завершения, защищая от повторной выдачи.
- Реальную рекламную SDK не подключать в рамках MVP.

## 23. Минимально достаточная проверка фичи

- После изменения проверить импорт ресурсов и ошибки скриптов, запустить соответствующий сценарий, проверить новую механику и затронутые старые механики.
- Исправлять обнаруженные ошибки текущей фичи до передачи на приёмку; не переносить их автоматически в backlog.
- Небольшие автоматические проверки использовать там, где они полезны: merge, формулы, сохранения, повторная выдача наград.
- Не создавать сложную тестовую инфраструктуру и тесты, повторяющие реализацию.
- Headless-проверки дополнять визуальной проверкой UI и ввода. Успешный запуск без окна не доказывает корректность управления или внешний вид.
- Перед проверками определить затронутые механики и риски. Во время реализации запускать целевые проверки; полный набор сохранённых сценариев обычно выполнять один раз после окончательных изменений общих игровых систем.
- После исправления повторять провалившуюся проверку и проверки затронутого поведения. Расширять или повторять весь набор только при новых изменениях, ошибках или конкретном непроверенном риске; объяснять причину дополнительных прогонов.
- Длительный игровой прогон выполнять прежде всего в целевой Web-версии, совмещая проверку новых механик, мыши/touch, масштабирования, рестарта и консоли. В Godot достаточно коротких целевых проверок; повторять длительный прогон на второй платформе, с другими seed или под нагрузкой только для конкретного риска.
- Повторный export нужен после изменений, влияющих на сборку. Приёмка, перенос отчёта, commit и push без изменений игрового кода или ресурсов не требуют повторных игровых тестов.

## 24. Ранний браузерный запуск

- Первый пробный Web export выполнить после технического фундамента как техническую проверку целевой платформы; повторять на ключевых этапах.
- Экспорт запускать через локальный HTTP-сервер, не через `file://`.
- Поддерживать воспроизводимый export preset и документировать реальные команды запуска и экспорта после проверки окружения.
- Финальная проверка включает полный игровой цикл, мышь и touch, масштабирование, звук после пользовательского действия, сохранения, browser console и производительность.
- Если устройство или браузер недоступны, явно указывать непроверенную часть, а не объявлять её проверенной.

## 25. Производительность по измерениям

- Не выполнять без необходимости поиск по всему дереву сцены каждый кадр; переиспользовать ссылки и ограничивать частоту поиска целей, когда это оправдано.
- Ограничивать срок жизни эффектов и damage numbers, проверять массовые волны и длительные сессии.
- Pooling и другие усложняющие оптимизации вводить после обнаружения конкретной проблемы и измерений.
- Game feel не должен ухудшать читаемость боя или производительность Web-версии.

## 26. Git и передача результата

- Репозиторий разработки: `https://github.com/mobigametim-bit/summoner_tower`; remote — `origin`.
- Перед изменениями проверять состояние рабочего дерева. Сохранять пользовательские изменения; не выполнять destructive reset, force push и перезапись чужой работы.
- Одна принятая фича — один отдельный логический commit с понятным сообщением, например `feat: implement unit merging`.
- После явной приёмки каждой фичи пользователем выполнять push её commit в `origin` без дополнительного запроса разрешения. Приёмка фичи является разрешением на публикацию относящихся к ней изменений.
- Перед push проверять diff и отсутствие временных файлов или секретов.
- Не коммитить `.godot/`, временные файлы, логи, локальные секреты и экспортированные сборки. Сохранять необходимые `.uid`, настройки импорта `.import`, исходные ресурсы и export presets без секретов.
- Не пересоздавать UID и не ломать ссылки при переносе или переименовании ресурсов.
- В итоговом отчёте указывать результат для игрока, выполненные проверки, известные ограничения и короткий конкретный чек-лист ручной приёмки.
- Документацию обновлять только по фактическим изменениям и согласованным решениям; не отмечать непроверенное как завершённое.
- После явной приёмки фичи переносить отчёт о её реализации и проверках в `docs/done/` и обновлять ссылки на него. ТЗ и общий план разработки остаются в `docs/`.
